# ZCode-EE 企业管理后端（ZCode-Manage）：功能规划与语言选型

> 状态：v1.0（2026-11-23）。前提与范围已由用户确认；标“建议”的技术选型要在 M0 打样中验证。
> 依据：ZCode 开源源码 v4.0.0（`ZCode` 仓库 `a4b44451`）。文中 ZCode 源码路径均相对该仓库根目录。
> 证据标记：〔源码〕在 v4.0.0 源码中亲自核对；〔文档〕ZCode 仓库文档明文；〔调研〕读码调研结论，未逐条复核；〔推断〕推理所得，落地前需实测。

## 0. 一页结论

| 问题             | 结论                                                                                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 是什么           | ZCode-EE 是 ZCode 的企业版（Enterprise Edition）。ZCode-Manage 是它的管控平面，管人和设备、模型和密钥、策略和安全、用量、审计、版本和扩展。                                       |
| 怎么交付         | 随 ZCode-EE 客户端（基于开源代码维护的 fork）完全离线私有化部署。单机容器化起步，用户增长后迁到集群。                                                                             |
| 模型来源         | 客户私有云上的模型服务。管控平面自建模型网关，统一出口、配额和计量。                                                                                                             |
| 登录             | 客户通过企业内部 SSO 登录。管控平面用可插拔的鉴权适配器调用客户的鉴权接口，客户端只对接管控平面。                                                                                 |
| 用什么写         | TypeScript（Node.js 24）全栈。管控平面、模型网关、管理控制台、客户端改造用同一门语言和同一套工具链。                                                                             |
| 一期范围         | 身份与席位、设备与分发、模型网关、受管策略、用量计量、平台审计、部署交付，共 7 个模块（第 5 节 P0）。                                                                           |
| 客户端           | 14 个改造点（第 6 节），一期 11 个。全部 14 个里有 9 处要改 ZCode 既有代码，最关键的是三处：新增受管配置层、修正 `yolo` 对禁用规则的绕过、解锁桌面更新源。                      |
| 团队套餐怎么处理 | 不拆。企业构建里禁用官方套餐界面，在模型凭据通道上并列新增一种企业接入类型（4.4 节）。                                                                                           |
| 最大风险         | 上游节奏快（近两个月 12 个版本），fork 的合并成本取决于改造点是否足够少、足够独立。                                                                                               |

| 前提         | 结论                                       | 对本方案的影响                                                                                               |

| 信创         | 暂不考虑                                   | 不为国产芯片、操作系统和数据库做适配                                                                         |

### 2.2 三个决定性事实

1. **ZCode 预留了管控平面的位置，但没有实现任何一部分。** 多端架构计划“明确不做”中心 Hub、多用户和角色授权；联邦架构图里的 “Account Control Plane（Model Profile、Credential policy / bindings、Federated Task View Profile）”至今是空位。ZCode-Manage 填的就是这个位置。〔文档〕
2. **只靠环境变量改地址，管不住。** `ZCODE_BASE_URL` 等变量能把客户端指向企业服务器，但配置的末两级（Env、Cli）归用户控制，`yolo` 又排在 deny 规则之前。不改代码，管理员下发的任何“策略”用户都能自己解除。这是需要维护 fork 的直接原因。〔源码〕
3. **上游的不变量值得继承。** 上游要求“业务真相只在任务来源节点；Hub、relay 和 Desktop main 不持有 conversation 业务状态”。管控平面只收上报副本和计量数据，不充当会话的权威，这样既能与二期的云端 Agent 架构对接，也能避免再建一套会话同步系统。〔文档〕

### 2.3 团队套餐在代码里的位置

- **两种接入类型。** Provider 的 `access` 是联合类型：`api-key`（含 `zhipu-coding-plan-api-key`）和 `zhipu-account`。后者用 `mode` 区分 `start-plan`、`individual-coding-plan`、`team-coding-plan`、`off-peak`、`highspeed`。〔源码〕`packages/provider/src/config/provider-data-schema.ts:14-60`
- **团队套餐只是其中一个 mode。** 目录里它的端点是 `https://api.z.ai/api/anthropic` 和 `https://open.bigmodel.cn/api/anthropic`。〔源码〕`config/provider/zcode-builtin.json`
- **有一条凭据通道。** Agent 发起账号型模型请求前，会向 Host 发起一次运行时请求头请求；Host 的 `resolveCurrent()` 按 `planKind` 换出短期令牌，随应答交回 Agent。团队套餐在这里用组织、项目、商品三个字段确定范围。〔源码〕`packages/services/src/zcode-agent/zcodeAgentService.ts:1790-1821`、`packages/services/src/model-provider/accountProviderRequestAuthService.ts:83-123`
- **这条通道绑定两个账号家族。** 通道上的类型 `zcodeAccountAccessSchema` 按 `planKind` 分支，每个分支都限定 `type` 为 `zhipu-account`、`family` 为 `zai` 或 `bigmodel`。〔源码〕`packages/shared/src/zcode-protocol/index.ts:1250-1275`
- **分布很散。** 非测试源码里提到团队套餐的文件有 44 个：界面层 33 个，服务层 9 个，共享类型与桌面各 1 个；提到 coding plan 的有 211 个。〔源码〕本次关键词检索统计，只反映量级

## 3. 产品定位

### 3.1 一句话定位

ZCode-EE 是 ZCode 的企业版。ZCode-Manage 是它的管控平面，随 ZCode-EE 客户端一起完全离线、私有化交付给企业客户。

### 3.2 角色

| 角色               | 是谁                             | 主要诉求                                             |
| ------------------ | -------------------------------- | ---------------------------------------------------- |
| 我方交付与支持     | 产品方的交付工程师、支持工程师   | 部署、升级、许可证签发、排障                         |
| 企业管理员         | 客户 IT                          | 组织、账号、席位、安装分发、版本升级                 |
| 安全管理员与审计员 | 客户安全或合规部门               | 策略发布、敏感数据防护、审计检索与导出（只读加发布） |
| 部门负责人         | 研发团队负责人                    | 本部门的用量、成员活跃度                             |
| 员工               | 使用 ZCode-EE 客户端的开发者     | 只使用客户端；可自助查看个人用量、解绑设备           |
| 服务账号           | CI 与自动化脚本                  | 用令牌调用模型网关，配额独立核算                     |

发布策略的角色和检索审计的角色要分开，避免同一个人既制定规则又负责查证。

### 3.3 形态与边界

- **一期**：员工本机桌面与 CLI，加管控平面。单机容器化部署，完全离线。
- **二期**：在管控平面下托管云端 Agent 节点；部署形态扩展到集群。
- **不做的事**：
  - 不在管控平面持有会话的权威状态，只收副本和计量。
  - 不改 ZCode 的会话协议与 RPC。
  - 一期不做多租户 SaaS。数据模型以组织为根作用域，默认一套部署一个组织。
  - 不重做 IDE 和聊天界面。
  - 不做厂商的套餐购买与支付。
  - 暂不做信创适配。

## 4. 总体架构

### 4.1 部署视图

```text
员工电脑（内网，无外网）
└─ ZCode-EE 客户端（fork 构建：桌面与 CLI）
   ├─ 企业登录与设备身份（只对接管控平面）
   ├─ 受管策略层（优先级高于 Env 与 Cli）
   ├─ 模型请求：带管控平面签发的短期令牌，指向企业模型网关
   └─ 用量与审计事件上报（本地排队后发送）
        │ HTTPS
        ▼
ZCode-EE 管控平面（单机容器化，Docker Compose）
├─ manage-api      控制面（模块化单体）：
│                  鉴权适配器、身份与席位、设备与分发、策略中心、
│                  模型与密钥、审计、运营分析、内部市场
├─ model-gateway   数据面：验令牌、配额与限流、转发、流式回传、计量
├─ ingest          数据面：接收用量、审计、遥测事件
├─ console         管理控制台 Web（React，桌面与手机浏览器自适应）
├─ postgres        事实库
├─ redis           限流计数、队列、缓存
└─ minio           安装包、插件包、预装工具、归档

出站只有两类，目标都在客户内网：
  model-gateway ── 客户的私有云模型服务（OpenAI 或 Anthropic 兼容端点）
  manage-api    ── 客户的内部鉴权接口
```

控制面和数据面分成两个可部署单元。模型请求是长连接流式转发，用量大时要独立扩容，不应该和管理接口抢同一个进程；两者放在同一个仓库、用同一套契约。

### 4.2 状态所有权

| 状态                   | 唯一所有者                  | 其他位置                     |
| ---------------------- | --------------------------- | ---------------------------- |
| 用户、组织、角色       | manage-api（PostgreSQL）    | 客户端只缓存登录态           |
| 席位与许可证           | manage-api                  | 客户端持有签名副本           |
| 设备身份与吊销         | manage-api                  | 客户端保存设备刷新令牌       |
| 策略草稿与已发布版本   | manage-api                  | 客户端只持已验签的副本       |
| 私有云端点的访问密钥   | manage-api 写入，网关读取   | 永不下发到客户端             |
| 实时配额计数           | model-gateway（Redis）      | 报表以 PostgreSQL 汇总为准   |
| 用量明细               | 网关产生，PostgreSQL 保存   | 客户端上报只补充维度         |
| 会话正文               | 客户端 Agent CLI            | 管控平面只存策略允许的归档副本 |
| 发行包与渠道           | manage-api 与对象存储       | 客户端按清单拉取             |

### 4.3 客户端接入策略

客户端访问的官方接口没有公开契约，接管时要区别对待：

| 方式     | 做法                                                           | 适用                                      | 代价                                                 |
| -------- | -------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------- |
| 端点替换 | 构建时把 origin 指向管控平面，由它实现同路径接口               | 强更与功能开关（`client/configs`）、更新清单 | 上游随时可能改接口；每接管一个都要配一份契约测试     |
| 专用接口 | fork 新增企业模块，使用版本化接口（`/em/v1/*`）和共享的 zod 契约 | 登录、设备注册、策略、模型目录、审计、归档  | 要多写一个客户端模块，但契约自己掌控                |
| 直接禁用 | 企业构建里关掉官方入口                                         | 登录、套餐、分享、奖励、闲时任务           | 要逐一确认没有残留的外联请求                         |

原则：只需改地址且语义吻合的，用端点替换；需要新语义的，用专用接口；对企业没有意义的，禁用。完全离线交付时，第三类是默认选项。

### 4.4 与团队套餐代码的关系

问题是：把团队套餐的对接部分拆掉，换成我们的模块，能不能无缝对接？

**结论：方向对，做法要改，而且它只覆盖模型接入这一条线。** 改造点编号见第 6 节。

1. **对的地方是接缝。** 团队套餐的做法正好是企业版需要的样板：令牌由 Host 集中签发，每次请求现取，短期有效，带范围校验，Agent 不落盘。企业接入类型加在这条通道上，同时解决了密钥托管、设备吊销和配额归属三件事。
2. **不能拆。** 团队套餐不是独立模块。它和个人版、Start、闲时、高速卡共用同一套账号框架和同一段换证代码（2.3 节），散在 44 个文件里，其中四分之三是界面。拆掉等于在上游最活跃的地段做大面积删除，每周同步都会冲突。正确做法是禁用（T14）：企业构建不带账号型 provider，隐藏套餐、购买和额度界面。入口少，冲突小。
3. **要并列新增，不要塞进现有类型。** 现有通道的每个分支都绑定 Z.AI 或 BigModel 账号家族。企业接入类型应作为平等的新成员加入（T5），现有分支一行不动。上游继续改它的套餐，我们继续改自己的。
4. **“无缝”只到模型接入为止。** 通道之外还有五类事必须做，换哪个模块都代替不了：
   - 登录：现有登录写死了两家的授权流程（T4）。
   - 策略强制：没有受管配置层，`yolo` 还排在禁用规则之前（T1、T2、T3）。
   - 启动引导与心跳：设备、策略版本、模型目录从哪来（T6）。
   - 上报：用量与审计事件往哪送（T7）。
   - 离线运行：更新源被锁、官方地址写死、外联要清干净（T8、T9、T10、T14）。

术语澄清：多端架构文档（`docs/architecture/unified-zcode-lite-server-multi-server-plan.md`）讲的是桌面、Web、手机和远端服务器之间怎么连接，里面没有团队套餐内容。团队套餐在代码和 `docs/coding-plan-enterprise.md` 里。

### 4.6 登录对接企业内部 SSO

- **管控平面是唯一的登录入口。** 客户端和管理控制台都走标准的 OAuth 授权码加 PKCE，对接管控平面。
- **客户差异收在鉴权适配器里。** 适配器做三件事：校验登录凭据，取回用户身份（外部 ID、姓名、工号、部门、组），以及在用户被停用或注销时联动失效。
- **适配器的两种形式。** 内置标准适配器覆盖常见协议；客户的自定义鉴权接口优先用配置化映射（接口地址、字段映射、签名方式），特殊协议在交付时写一个适配器。
- **这样做的好处。** 客户端只开发一次；客户的密钥只存在于管控平面；登录、席位、吊销和审计在同一处。
- **不建议的做法。** 让客户端直接调用客户的鉴权接口。那样每个客户都要定制客户端，每加一家客户就多一套登录代码。

## 6. 企业版客户端改造点

### 6.1 原则

1. **新增优先。** 企业能力放进独立模块，既有代码只在少数接缝处接线。
2. **禁用优先于删除。** 官方功能在企业构建里用开关关掉，不删代码。
3. **接缝有清单。** 每个改造点登记在下表。每次同步上游，逐项确认是否受影响。
4. **企业行为靠编译开关。** 沿用 ZCode 现有的构建期常量机制（`__ZCODE_*__`）注入企业端点，开源默认行为不变，便于持续和上游对比。
5. **契约先行。** 客户端与管控平面之间的接口用 zod 定义在独立包里，两边共用，并配契约测试。
6. **安全修复回传上游。** 发现的上游安全问题优先提 PR，减少长期分叉。

## 7. 语言与技术选型

### 7.1 结论

用 TypeScript 做全栈：控制面、数据面、控制台、客户端改造全部用 TypeScript，运行时统一为 Node.js 24。

### 7.2 为什么是 TypeScript

1. **被管理的东西也是 TypeScript。** 管控平面的难点不在增删改查，而在和客户端的接缝：配置怎么合并、权限按什么顺序判定、凭据从哪条通道取。这些逻辑都在 ZCode 源码里。同一种语言才能直接拿客户端的模块来写测试，比如在管控平面的测试里加载 fork 的配置合并器，验证一条策略下发后的实际合并结果。跨语言就只能重写一遍，重写就会走样。
2. **工具链完全一致。** ZCode 用 Node.js 24.14.0、pnpm 10.33.2、TypeScript 6、zod 4、Vitest、oxlint 与 oxfmt、`tsc -b` 项目引用。〔源码〕`package.json`、`mise.toml` 管控平面照搬同一套，fork 与管控平面可以共享 CI 配置和代码规范。
3. **二期的运行时本来就是 Node。** 云端 Agent 节点跑的是 `zcode`，服务端 `@zcode/server` 是 Hono 4 写的。〔源码〕`packages/server/package.json` 用 TypeScript 写管控平面，只需维护一套运行时和运维经验。
4. **界面可以延续。** 控制台可以沿用 ZCode 的 `DESIGN.md` 和基础组件风格，交付给客户的界面与客户端一致。整包依赖 `@zcode/ui` 要谨慎，它与 ZCode 的服务层耦合较深，建议只复用设计规范和基础组件。〔推断〕
5. **流式转发性能足够。** 模型网关是 I/O 密集的长连接转发，Node 24 原生的 `fetch` 和流式处理可以支撑数百到数千名开发者的企业规模。〔推断〕上线前要用压测确认。

TypeScript 不擅长的部分是重 CPU 的统计分析。将来如果用量分析的性能不够，可以把聚合计算移到列式数据库里做，不影响主体选型。

### 7.3 其他语言的位置

| 语言               | 适合的情形                                                           | 这次不选的原因                                                                   |
| ------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Python（FastAPI）  | 团队只会 Python，且后端不碰客户端                                    | 这次要深度维护 fork，跨语言多一层翻译；控制台仍要写 TypeScript；无法复用 ZCode 的协议定义 |
| Go                 | 追求单二进制交付的高并发网关或 relay（上游内部服务端是 Go 仓库，relay 推测在其中） | 管理功能的开发效率低，同样跨语言。将来网关成为瓶颈时，可以单独重写网关         |
| Java（Spring Boot） | 客户硬性要求 Java 技术栈                                             | 与 ZCode 无法复用，迭代慢，前端仍要 TypeScript                                   |

### 7.4 技术栈（建议，M0 验证）

| 层           | 选型                                                     | 理由                                                                                   |
| ------------ | -------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 运行时       | Node.js 24，TypeScript 6（严格模式）                     | 与 ZCode 的 `engines` 和 `mise.toml` 一致                                              |
| 工程         | pnpm workspace、`tsc -b`、Vitest、oxlint、oxfmt          | 与 fork 同一套                                                                         |

| 数据访问     | Drizzle ORM，迁移用 SQL 文件                             | 轻量，没有引擎二进制，离线交付友好，迁移可以评审                                      |
| 缓存与队列   | Redis 7，BullMQ                                          | 限流计数、异步聚合、通知                                                               |

### 7.5 界面形态

做响应式网页，不做原生 App。管理操作集中在桌面浏览器，手机上只需要看报表和处理审批，自适应网页足够。需要推送到手机的事项（审批、告警）走客户内网的 IM 机器人消息，点开即网页。原生 App 的多端维护成本，对管控平台不划算。

## 8. 关键流程

带箭头的步骤里，箭头左侧是发起方，右侧是接收方，编号即先后顺序。

### 8.1 首次登录与设备注册

```text
① 客户端 ── 启动，请求引导配置（登录入口、最低版本）──► 管控平面
② 客户端 ── 打开授权页（PKCE 加 state）──► 管控平面 ── 跳转登录 ──► 客户的内部鉴权接口
③ 管控平面：用适配器向客户系统确认身份；首次登录自动建账号，校验席位；通过后向客户端发放授权码
④ 客户端 ── 用授权码和 PKCE 换取令牌 ──► 管控平面签发短期访问令牌和与设备绑定的刷新令牌
⑤ 客户端 ── 注册设备（指纹、版本、系统）──► 管控平面
⑥ 客户端 ── 拉取策略和模型目录 ──► 管控平面
⑦ 管控平面：写入审计事件（登录、设备注册）
```

吊销设备即吊销它的刷新令牌；访问令牌到期后无法续期，模型调用随之失败。

### 8.2 一次模型请求

```text
① Agent ── 发起账号型请求前，向 Host 索取凭据 ──► Host 从企业模块取得短期令牌并交回
② Agent ── 带令牌的流式请求 ──► 网关
③ 网关：本地校验令牌签名和有效期，得到用户、设备、组织
④ 网关：向 Redis 预检配额余量、并发数、请求频率；不足则直接拒绝，不到达私有云
⑤ 网关：按模型别名选端点，流式转发 ──► 客户私有云 ── 流式响应 ──► 网关 ── 边转发边解析用量 ──► Agent
⑥ 网关：按实际用量扣减配额，把用量事件（以请求 ID 为幂等键）写入队列
⑦ 后台任务：批量写入 PostgreSQL 明细，再汇总成分钟、小时、天
⑧ 客户端：请求结束后上报会话与工具维度（补充信息，可延迟）
```

第 ① 步走的是 ZCode 现有的凭据通道（2.3 节）。两点约束：token 数量要到响应结束才确定，所以配额是“请求前预检，响应后结算”，需要硬性预算的场景再预留最大输出额度；用量以网关记录为准，客户端上报只用来补充维度。

### 8.3 策略发布与生效

```text
① 管理员 ── 保存草稿 ──► 管控平面（草稿不生效）
② 管理员 ── 发布 ──► 管控平面生成版本 N（内容、签名、生效时间）
③ 客户端 ── 心跳时发现新版本 ──► 拉取 ──► 验签 ──► 写入受管作用域 ──► 必要时提示重启
④ 客户端 ── 回报已生效版本 N ──► 管控平面记录
⑤ 控制台：列出尚未到达版本 N 的设备，可按配置限制这些设备调用模型
```

生效与否以版本号和客户端回执为准，不靠固定的等待时间来猜。

### 8.4 版本发布与更新

```text
① 我方 CI（联网环境）── 构建企业版并注入企业端点 ──► 签名与公证 ──► 制作离线升级包
② 交付人员 ── 把升级包导入管控平面 ──► 创建发布（渠道、灰度规则）
③ 客户端 ── 启动时读取最低版本和自己所在的渠道 ──► 管控平面
④ 客户端 ── 请求更新清单 ──► 管控平面按设备标识决定目标版本
⑤ 客户端：低于最低版本则强制更新；否则按渠道从内网下载，校验后安装，并上报新版本
⑥ CLI：通过内网的安装脚本和版本索引更新
```
