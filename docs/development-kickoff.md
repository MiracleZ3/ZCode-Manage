# ZCode-EE 开发启动计划：从准备到第一个纵向链路

> 状态：v0.3（2026-11-23）。Step 0 已完成，Step 1 未开始；执行记录见第 9 节。
> 上游文档：[功能规划与语言选型](enterprise-backend-features-and-language.md)（下称“方案文档”）。
> 文中 ZCode 源码路径相对本地源码目录，即 fork 仓库 `ZCode-EE` 的检出。

## 0. 一页结论

**先打通一条最细的纵向链路，再按纵向链路逐个加功能。** 第一条链路是：企业登录，一次模型调用，用量入库。

不走两条弯路：不“先把管理端做完再对接客户端”，也不“先把 fork 改完再做管理端”。两端的接缝才是最大的不确定点，要尽早合龙。

三个贯穿始终的原则：

1. **契约先行。** 客户端与管理端之间的接口，先用 zod 定下来，两端共用同一份定义。
2. **新增优先，禁用优先。** fork 里企业代码集中在新增目录，既有代码只留接缝；官方功能只关不删。
3. **每一步都有可演示的出口。** 做完一步，能看到一个结果，才做下一步。

```text
Step 0 准备 ──┬─► Step 1 契约与开发栈（管理端）──┐
              └─► Step 2 客户端接缝打样（fork）───┴─► Step 3 第一个纵向链路 ─► 纵向链路 2、3…
```

Step 1 和 Step 2 可以交替进行，互不阻塞。

## 1. 仓库与分支（已完成）

| 仓库           | 远端与分支                                                                 |
| -------------- | -------------------------------------------------------------------------- |
| `ZCode-EE`     | `upstream` 是官方 `zai-org/ZCode`，只用来同步；`origin` 是 fork             |
| 同上           | `main` 跟踪 `upstream/main`，只做快进同步，不放企业版提交                   |
| 同上           | `ZCode-EE-GLM` 跟踪 `origin/ZCode-EE-GLM`，承载全部企业版提交；本地已检出   |
| `ZCode-Manage` | `origin` 是 `MiracleZ3/ZCode-Manage`，`main` 分支                           |

本地源码目录的基线检查（`node scripts/check-workspace-freshness.mjs`）在新布局下照常工作。它报告的“相对 `origin/main`”此时表示企业分支落后于已同步的官方主线多少个提交。

**每周同步上游**

```sh
git fetch upstream --prune --tags
git switch main && git merge --ff-only upstream/main && git push origin main
git switch ZCode-EE-GLM && git merge main
# 然后跑门禁：pnpm typecheck、pnpm lint、pnpm test:engineering、契约测试
```

同步后记录两件事：冲突的文件分别对应哪个改造点；门禁里哪些告警是上游自带的。

## 2. fork 里的企业代码放在哪里

| 内容                     | 建议位置                              | 说明                                                         |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------ |
| 企业登录、启动引导、心跳 | Host 侧新增一个 workspace 包          | 通过现有 `Providers` 注入点接线，不改既有服务的内部实现       |
| 策略加载与验签           | Host 侧同一个包，加 Agent 运行时一处  | Agent 侧只负责把受管配置并入自己的配置合并                    |
| 模型令牌续期             | Host 侧同一个包                      | 在凭据通道上并列新增企业接入类型                             |
| 事件上报队列             | Host 侧同一个包，加 Agent 运行时一处  | 本地排队、可重试、可关闭                                     |
| 企业构建开关             | 构建期常量                           | 沿用 ZCode 现有的 `__ZCODE_*__` 机制，开源默认行为不变        |
| 每项改动的规格           | `docs/ee/<主题>.md`                  | 遵循 ZCode 仓库“先改规格再实现”的规定                        |
| 与管理端共享的契约       | fork 内一个固定目录                  | 由管理端生成后同步进来，不手改；校验和进入版本控制           |

包名与目录名在 Step 2 的第一个提交里确定。改造点编号（T1 到 T14）见方案文档 6.2 节，fork 里每个提交都要在说明里写明属于哪个编号。

## 3. 管理端的起步形态

M0 只需要四个自研或现成组件加三个开发用的替身。

| 组件           | M0 的最小职责                                                              |
| -------------- | -------------------------------------------------------------------------- |
| `manage-api`   | 签发令牌、设备注册、下发策略与模型目录；配置校验、日志、数据库迁移、健康检查 |
| `model-gateway`| 验令牌、转发到私有云、记一条用量                                           |
| `console`      | 登录页和空壳，能显示用量明细表即可                                         |
| `contracts`    | 第 4 节全部接口的 zod 定义，生成 OpenAPI                                   |
| Keycloak       | 开发用的替身：模拟客户的企业身份系统                                       |
| mock 模型服务  | 开发用的替身：先实现 OpenAI Chat Completions，再补 Anthropic Messages              |
| 基础设施       | PostgreSQL、Redis、对象存储，全部由 Docker Compose 拉起                     |

`ingest` 在 M0 先作为 `model-gateway` 进程内的一个模块，用量大起来之后再拆成独立单元。

开工第一天给 `ZCode-Manage` 写 `AGENTS.md`，约定工程规则，沿用 ZCode 源码仓库的做法：规格先行、每个状态只有一个所有者、`typecheck` 与 `lint` 必跑、日志分级。

## 4. 最先定下来的契约

| 编号 | 接口                         | 用途                                                   |
| ---- | ---------------------------- | ------------------------------------------------------ |
| C1   | `GET /em/v1/bootstrap`       | 启动引导：登录入口地址、最低版本、心跳间隔              |
| C2   | OAuth 2.0 授权码加 PKCE      | 客户端与控制台登录，标准端点由 `oidc-provider` 提供   |
| C3   | `POST /em/v1/devices` 与心跳 | 设备注册；上报版本和已生效的策略版本                   |
| C4   | `GET /em/v1/policy/current`  | 带签名和版本号的策略文档                               |
| C5   | `GET /em/v1/models`          | 模型目录，客户端据此生成只读的受管 Provider            |
| C6   | `POST /em/v1/events/batch`   | 用量、审计、客户端事件的批量上报，带幂等键             |
| G1   | OpenAI Chat Completions 端点 | 网关。客户私有云走 OpenAI 协议，先做                   |
| G2   | Anthropic Messages 端点      | 网关。ZCode 内置的账号型 provider 全部用这个协议，第二做 |
| G3   | OpenAI Responses 端点        | 网关。有客户需要时再做                                 |

`/em/v1` 是专用接口，前缀和路径都是建议，Step 1 写契约时定稿。4.3 节方案文档里的“端点替换”（强更开关、更新清单）留到纵向链路 5 再接管。

**契约怎么共享。** 定义只写在 `ZCode-Manage/packages/contracts`。同步脚本把生成物放进 fork 的固定目录，fork 的构建不依赖网络和另一个仓库。两边 CI 各校验一次生成物的哈希，不一致就失败。离线交付不受影响。

## 5. 开发顺序

### Step 0 准备

- fork 已指向 fork 仓库并切到企业分支（已完成）。
- 安装依赖：`pnpm bootstrap`。Node 24 即可，仓库的 CI 断言只要求主版本号不低于 24；要和官方构建完全一致，就按 `mise.toml` 装到 24.14.0。pnpm 由 corepack 按仓库声明自动取 10.33.2。
- 记录上游基线：在未改动的 `ZCode-EE-GLM` 上跑 `pnpm typecheck`、`pnpm lint`、`pnpm test:engineering`，把结果存档。上游本来就有若干告警，存档是为了分清哪些不是我们引入的。
- `ZCode-Manage`：写 `AGENTS.md`，建 workspace 骨架和 CI（`typecheck`、`lint`、测试）。

**出口：** 两个仓库都能一键跑通质量门禁，上游基线有存档。

### Step 1 契约与开发栈（管理端）

- 在 `contracts` 里写第 4 节全部接口的定义，生成 OpenAPI。
- 写开发栈的 Compose 文件，拉起第 3 节的全部组件。
- 搭三个应用的骨架：`manage-api`、`model-gateway`、`console`。
- **出口：** 用 curl 模拟一个客户端：登录拿到令牌，调网关，PostgreSQL 的用量表里多一行。

### Step 2 客户端接缝打样（fork）

每个改造点单独一个提交，先写 `docs/ee/` 里的规格，再写测试，最后实现。按这个顺序做：

1. **受管配置与权限顺序（T1、T2、T3）。** 最先做，它决定策略能不能被强制。出口：下发的禁用工具在 `yolo` 模式下同样生效，设置界面里对应项为只读。
2. **企业登录与启动引导（T4、T6）。** 出口：企业账号能登录，设备完成注册并上报心跳。
3. **企业接入类型（T5）。** 出口：客户端只看得到被允许的模型，令牌不出现在任何本地文件里。
4. **更新源解锁（T8）。** 出口：打包版从指定的企业地址读取更新清单。

每一项都要求：单测通过；`pnpm typecheck`、`pnpm lint`、`pnpm architecture:check --changed` 通过；桌面和 CLI 两种形态各手动验证一次。四项做完后做一次上游同步，把冲突数记下来。

### Step 3 第一个纵向链路（两端合龙，M0 结束）

1. 企业版客户端指向开发栈。
2. 用 Keycloak 里的账号登录，设备注册，拉到策略和模型目录。
3. 客户端里只出现受管模型。发一条消息，网关转发给 mock 模型服务，控制台里出现这条用量。

验证方式是一段端到端脚本加一次录屏。再在断网环境里重跑一遍，除了开发栈之外没有外网，记录下所有外联尝试，这是离线外联清单的初稿。

**M0 的出口：** 四个接缝打通；契约定稿；与上游的合并成本有实测数字；离线外联清单有初稿。

### Step 4 之后的纵向链路

| 顺序 | 纵向链路         | 内容                                                             |
| ---- | ---------------- | ---------------------------------------------------------------- |
| 2    | 策略闭环         | 编辑策略，签名发布，客户端生效并回执，控制台显示未合规设备     |
| 3    | 配额与用量       | 预算、限流、超额策略、用量报表                                 |
| 4    | 席位与许可证     | 席位分配、超限处理、许可证校验                                 |
| 5    | 分发             | 离线包托管、最低版本、更新清单、设备清单；签名与公证在此前办妥 |
| 6    | 审计与吊销       | 平台审计、活动审计、吊销设备后立即失效                         |

每条纵向链路都走同一套流程：写规格，先写会失败的测试，最小实现，跑门禁，小步提交。六条做完，方案文档里一期（P0）的功能就齐了。

## 6. 每一项改动的工作方式

适用于我们两人的协作。

1. **先写规格。** 管理端写在 `ZCode-Manage/specs/`，fork 写在 `docs/ee/`。规格里写清规则、状态归谁、接口和验收场景。
2. **先写验收。** 管理端是契约测试和集成测试；控制台的交互改动先写端到端测试；fork 是单测加相关的端到端用例。
3. **最小实现。** 只改完成这一项必需的地方，fork 里不属于任何改造点编号的既有代码不动。
4. **跑门禁，如实报告。** fork：`pnpm typecheck`、`pnpm lint`、`pnpm architecture:check --changed`；管理端：`typecheck`、`lint`、测试。失败就写失败，不把已有的失败说成通过。
5. **小步提交。** 提交说明用 Conventional Commits，fork 里注明改造点编号。推送之前先问。
6. **每周同步上游**，做法见第 1 节。

## 8. M0 不做的事

- 不做控制台的完整功能页，只做登录和一张用量表。
- 不引入 ClickHouse、Kubernetes、Helm。
- 不做自建 relay、IM 机器人、云端 Agent。
- 不删除任何官方代码。
- 不办签名和公证，纵向链路 5 之前再办。
