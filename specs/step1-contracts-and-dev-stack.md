## 1. 范围

**做：**

- 把两端要用的接口定义成 zod 契约，生成 OpenAPI。
- 管控平面自己充当客户端的 OIDC Provider：服务账号走 `client_credentials`，人和交互式客户端走授权码加 PKCE。
- 第一个鉴权适配器：标准 OIDC 上游。开发环境用 Keycloak 充当客户的企业身份系统。
- 模型网关的第一个端点：OpenAI Chat Completions，含流式透传，记一条用量。
- PostgreSQL 里的最小数据集：用户、设备、模型目录、用量明细。
- 开发用的替身：一个假的 OpenAI 兼容模型服务。
- 控制台骨架：登录页、一张用量明细表，以及带确认页的退出登录。
- 集成测试与一条用 curl 走通出口的脚本。

**不做，留给后续：**

- `POST /em/v1/events/batch`（C6）只定义契约，不实现。Step 2 起客户端上报时再做。
- 策略（C4）只定义契约。策略的签发、生效核验在纵向链路 2。
- 配额、限流、席位、许可证。
- 数据库里不存任何密钥。上游模型的访问密钥用环境变量名引用。
- OIDC 的授权、会话等状态用 `oidc-provider` 的内存适配器。单实例开发够用；持久化适配器属于一期。**注意它对部署的影响：服务一重启，所有会话和刷新令牌全部失效；多副本部署下根本不能工作。所以容器化交付之前必须换成持久化适配器。** 已列入方案文档 4.5 节的交付前检查清单；用户 2026-11-23 要求到交付时提醒，届时要主动提出。
- Redis 和对象存储本期不启动，因为没有代码用到。用到时再加进开发栈。
- 客户端一侧的令牌续期流程（到期前自动续、续不上时重新登录），以及令牌与设备的绑定。属于 Step 3。颁发者一侧的刷新授权与吊销端点本期已实现，见第 4 节。
- 退出登录时一并结束客户身份系统那边的会话（单点登出）。本期只结束管控平面自己的会话，后果见第 11 节。**已决定暂不做（2026-11-23）：用户明确说暂不考虑共用电脑的场景。**

## 2. 入口

| 入口                       | 谁在用                         | 说明                                             |
| -------------------------- | ------------------------------ | ------------------------------------------------ |
| OIDC 端点 `/connect`       | 交互式客户端、服务账号、控制台 | 授权、换令牌、公钥、吊销、结束会话               |
| `/interaction/*`           | 浏览器（登录流程中）           | 管控平面自己的交互路由：开始登录、登录收尾、自动同意 |
| `/auth/callback/*`         | 浏览器（从客户身份系统回来）   | 第一类适配器的回调                               |

| `/em/v1/usage/*`           | 控制台                         | 用量明细                                         |
| `/gateway/v1/*`            | 企业版客户端里的模型请求       | OpenAI 兼容端点                                  |

## 3. 契约

路径与字段是实现的主要依据；`packages/contracts` 里的 zod 定义是唯一来源。

| 编号 | 接口                                | 鉴权                | 鉴权范围          | 本期     |
| ---- | ----------------------------------- | ------------------- | ----------------- | -------- |
| C1   | `GET /em/v1/bootstrap`              | 无                  |                   | 实现     |
| C2   | OIDC：授权码加 PKCE、`client_credentials`、刷新、吊销、结束会话 | 见第 4 节 |        | 实现     |
| C3   | `POST /em/v1/devices`               | 访问令牌            | `device:register` | 实现     |
| C3   | `GET /em/v1/devices`                | 访问令牌            | `device:register` | 实现     |
| C4   | `GET /em/v1/policy/current`         | 访问令牌            |                   | 仅契约   |
| C5   | `GET /em/v1/models`                 | 访问令牌            |                   | 实现     |
| C6   | `POST /em/v1/events/batch`          | 访问令牌            |                   | 仅契约   |
| G1   | `POST /gateway/v1/chat/completions` | 访问令牌            | `model:invoke`    | 实现     |
| G1   | `GET /gateway/v1/models`            | 访问令牌            | `model:invoke`    | 实现     |
| U1   | `GET /em/v1/usage/events`           | 访问令牌            | `usage:read`      | 实现     |

**C1 引导配置。** 公开可读。返回登录入口（`issuer`、`authorizationEndpoint`、`tokenEndpoint`、`jwksUri`）、网关地址、最低客户端版本、心跳间隔秒数。客户端启动时请求一次。

**C5 模型目录。** 返回 `models[]`，每项含 `id`（管控平面内的模型名，客户端就用它请求）、`displayName`、`contextWindow`、`endpointId`。只返回启用的模型。

**C3 设备注册。** 提交 `name`、`platform`、`clientVersion`，返回 `deviceId`。设备归属取自令牌的 `sub`，不接受调用方指定用户。

**U1 用量明细。** 按 `occurredAt` 倒序，`limit` 默认 50、上限 500，`cursor` 为上一页最后一行的 `occurredAt` 与 `id`。

**G1 请求与响应。** 请求体和响应体遵循 OpenAI Chat Completions 的形状，不额外造字段。鉴权失败返回 401，上游失败透传上游的状态码与响应体。

**另有一张契约之外的约定。** 请求 ID 用 `x-request-id` 请求头传递，每个响应都回传。

## 4. 身份与令牌

**颁发者。** `ZM_PUBLIC_BASE_URL`，例如开发环境的 `http://localhost:5173`。OIDC 端点在它的 `/connect/*` 之下。

**对外地址只认配置。** 颁发者公布的端点地址、登录流程里的跳转，一律由 `ZM_PUBLIC_BASE_URL` 派生，不从请求头里读。库默认按请求的 Host 与转发头来拼这些地址，那会带来两个问题：反向代理少传一个头、TLS 终止在代理那一层，端点就全错了；调用方伪造 Host，就能让发现文档给出指向别处的授权端点。所以进入库之前，入口把转发头统一改写成颁发者的协议与主机名，并拒绝请求行写成完整地址的请求。反向代理因此不必传递 Host 与协议头。网关核对令牌签发者用的是另一个变量 `ZM_ISSUER`，两者必须同值；开发环境的生成脚本让它们出自同一个常量。

**授权类型与客户端。** 本期的客户端由配置给定，不做动态注册。登录回调地址（`redirectUris`）与退出后的回跳地址（`postLogoutRedirectUris`，可选）都要逐个登记，没登记的那一步就会被拒绝。

| 客户端             | 类型     | 授权类型                 | 用途                               |
| ------------------ | -------- | ------------------------ | ---------------------------------- |
| 服务账号客户端     | 机密     | `client_credentials`     | 脚本、CI；也是出口脚本用的那一个   |
| 企业版客户端       | 公共     | 授权码加 PKCE、刷新      | 桌面与 CLI                         |
| 控制台             | 公共     | 授权码加 PKCE、刷新      | 浏览器                             |

**范围。** `openid`、`profile`、`offline_access`，以及自定义的 `model:invoke`、`device:register`、`usage:read`。

**申请刷新令牌的前提。** 授权请求要先拿到 `offline_access`，必须同时带 `prompt=consent`，这是 OpenID Connect 的规定。不带时颁发者不报错，只是按规范忽略这个范围：换到的令牌范围里没有它，也不发刷新令牌，于是访问令牌 15 分钟后到期就得重新登录。管控平面把“同意”这一步交给程序自动批准（见下面的时序），所以多出来的那一跳用户看不见。**企业版客户端和控制台发起登录时都必须带 `prompt=consent`。**

**令牌格式。** 访问令牌是 JWT，受众固定为 `{颁发者}/api`。管理接口和网关都用颁发者的公钥在本地验签，核对签名、颁发者、受众三项，不回查颁发者。客户端不必带 `resource` 参数：授权时管控平面把这个资源定为默认，换令牌和续期时沿用授权时定下的那一个。

“这个资源叫什么”只在 `packages/shared` 里定义一次，颁发者用它写受众，验签的一方用它核对。

**令牌里的声明。** 除标准声明外：`zm:accountType` 取 `user` 或 `service`；`zm:displayName`；`zm:orgId`。网关和 `/em/v1/*` 据此确定归属，不回查数据库。用户的令牌 `sub` 是管控平面里的用户标识，续期前后不变；服务账号令牌的 `sub` 是客户端标识。

**身份令牌与显示名。** 本期所有访问令牌都带受众，按库的规则不能用于用户信息端点（那边会拒绝），所以经 `profile` 范围获批的 `name` 放在身份令牌里，客户端不必查用户信息端点。库内置的“范围到声明”映射只有 `openid` 的 `sub`，必须在配置里写明 `profile` 带出 `name`，否则声明在签发时就被去掉，而且没有任何报错。

**有效期。** 访问令牌 15 分钟，刷新令牌 14 天，授权码 1 分钟，身份令牌 5 分钟。

**账号来源。** 两类：

- **用户。** 由鉴权适配器在首次登录时自动建档，按“适配器标识 + 外部主体”唯一。
- **服务账号。** 即 `client_credentials` 的客户端本身，没有用户记录。用量按客户端标识归属。

**鉴权适配器。** 客户的差异收在这一层，客户端只对接管控平面。

```ts
interface Identity {
  subject: string;
  displayName: string;
  email?: string;
}

// 第一类：把浏览器带到客户身份系统去登录
interface RedirectAuthAdapter {
  id: string;
  kind: "redirect";
  // 返回跳转地址，以及它对上游用的 PKCE 校验串。校验串要在两次调用之间保存，所以交还给调用方。
  buildAuthorizationUrl(input: { state: string; callbackUrl: string }): Promise<{ url: string; codeVerifier: string }>;
  finishLogin(input: { callbackUrl: URL; state: string; codeVerifier: string }): Promise<Identity>;
}

// 第二类（未实现）：客户提供“校验账号口令”一类接口，管控平面自己出登录页
// kind: "credentials"; verifyCredentials(...): Promise<Identity>
```

本期只实现第一类，即标准 OIDC 上游，地址是 `/auth/callback/{适配器标识}`。对上游固定申请 `openid profile email`，用授权码加 PKCE 换令牌，并用上游公钥验 ID Token 的签名。第二类在接口里留位置，Step 2 做。

**登录的事件顺序（第一类适配器）：**

```text
① 客户端 ── GET /connect/authorize（PKCE、state、prompt=consent）──► 管控平面
② 管控平面 ── 303 → /interaction/{uid}（登录；管控平面自己的路由）
③ /interaction/{uid} ── 生成 state 与 PKCE 校验串，加签后写进 Cookie ── 302 → 客户身份系统的授权地址
④ 浏览器在客户身份系统登录
⑤ 客户身份系统 ── 302 → /auth/callback/{适配器标识}（code、state）
⑥ 管控平面：核对 state，向上游换令牌并验签，归一出 Identity，首次登录自动建档
      ── 换成“这次交互、这个人”的加签 Cookie ── 303 → /interaction/{uid}/finish
⑦ /interaction/{uid}/finish：核对确实是这一次交互 ── 结束登录交互
⑧ 管控平面 ── 303 → /interaction/{uid}（同意）──► 程序自动批准全部申请范围，不向用户展示页面
⑨ 管控平面 ── 302 → 客户端的回调地址（code）──► 客户端用 code 与 PKCE 换令牌
```

**为什么登录分两步。** 颁发者把交互会话的 Cookie 限定在 `/interaction/{uid}` 这条路径下，浏览器只把它发给这条路径之下的请求。这是库有意的防护：只有交互路由才能结束一次交互。客户身份系统的回调地址是固定登记的，不在那条路径下，所以回调只能确认“是谁”，再把浏览器带到 `/interaction/{uid}/finish`，由那里结束交互。集成测试里的 Cookie 罐因此必须按路径挑着发；只按名字存取的版本会替浏览器发一个它不会发的 Cookie，把这里的问题遮住。

第 ③ 步写下的 Cookie 是 HMAC 加签的：内容不加密，但改一个字节就会被拒。它分两步，带步骤标记，互相不能顶替。第 ③ 步是“带去客户身份系统”：`state`、校验串、属于哪次交互、由哪个适配器发起。第 ⑥ 步换成“等人收尾”：哪一次交互、哪个人；`state` 与校验串用掉了，不再留着。整个过程 10 分钟有效。每一次核对都要求步骤与交互标识对得上，否则一律按“登录状态已失效”处理，不区分原因；同一个回调地址重放会被拦下。登录要往返客户身份系统，这份状态跟着浏览器走，服务端不必为它另存什么。

第 ⑧ 步不能省：颁发者靠它把批准的范围写进授权记录。客户端都是管控平面自己登记的，不存在向第三方授权的问题，所以由程序批准。

**退出登录的事件顺序：**

```text
① 客户端 ── GET /connect/logout（id_token_hint、post_logout_redirect_uri）──► 管控平面
② 管控平面：回跳地址已登记；把一次性令牌存进会话 ── 200 确认页
③ 使用者点“退出登录” ── POST /connect/logout/confirm（xsrf、logout=yes）──► 管控平面
④ 管控平面：结束会话 ── 303 → 登记过的回跳地址
```

确认这一步是库的设计：结束会话的那一下是表单提交，带一次性令牌，第三方页面没法把人悄悄登出。确认页与出错时的提示页都由管控平面自己出，只含内联样式和转义后的文字，并声明内容安全策略：库自带的同类页面会去加载外部字体，与完全离线交付冲突。

## 6. 数据模型

全部是本期需要的最小形态。

- `users`：`id`、`adapter_id`、`subject`、`display_name`、`email`、`created_at`；`(adapter_id, subject)` 唯一。
- `devices`：`id`、`user_id`、`name`、`platform`、`client_version`、`created_at`。

- `usage_events`：`id`、`request_id`（唯一，幂等键）、`occurred_at`、`subject_type`、`subject_id`、`subject_name`、`client_id`、`device_id`、`model`、`upstream_model`、`endpoint_id`、`input_tokens`、`output_tokens`、`total_tokens`、`status_code`、`stream`、`duration_ms`、`usage_source`。

迁移以 SQL 文件形式入库，服务启动时自动应用。种子数据的模型目录只在表为空时写入。

## 7. 网关：一次请求的事件顺序

```text
① 客户端 ── POST /gateway/v1/chat/completions（Authorization: Bearer）──► 网关
② 网关：本地用颁发者的公钥验签名，核对颁发者与受众；失败直接 401，不触达上游
③ 网关：检查范围含 model:invoke；按请求里的 model 查模型目录，禁用或不存在返回 404
④ 网关：把请求体里的 `model` 从目录里的模型名改写成上游模型名，把 Authorization 换成上游密钥，其余按原样转发到上游
⑤ 上游 ── 响应 ──► 网关：边转发给客户端，边解析
⑥ 网关：按解析结果写一条用量，request_id 为幂等键
```

用量的记法：

- 非流式：取响应体里的 `usage`，三个 token 数都是精确值，`usage_source` 为 `upstream`。
- 流式且请求带 `stream_options.include_usage`：取最后一个带 `usage` 的数据块，同样精确。
- 流式且没有 usage：本期仍记一条，token 数记为空，`usage_source` 为 `missing`。估算放到 Step 2，届时把 `tiktoken` 之类的估算结果记为 `estimated`。
- 上游返回 4xx、5xx 时也记一条，`status_code` 如实，token 数为空。
- 令牌不对或模型不存在不记：请求没有到上游。

配额预检本期恒为放行，位置留在第 ③ 步之后。

## 8. 错误码

| code                   | HTTP | 场景                                   |
| ---------------------- | ---- | -------------------------------------- |

| `validation_error`     | 400  | 请求体不符合契约                       |
| `internal_error`       | 500  | 未预期错误，细节只进日志               |

## 9. 开发栈

开发时只有**一个来源**：Vite 开发服务器的 `http://localhost:5173`。页面、管理接口、OIDC 端点都在它的地址下，由它代理到管理接口。管理接口没有开放跨域，所以浏览器里的每个请求都必须与页面同源；正式部署时由反向代理承担同样的角色，两边拓扑一致。

| 组件          | 运行位置     | 端口 | 说明                                             |
| ------------- | ------------ | ---- | ------------------------------------------------ |
| PostgreSQL 16 | 容器         | 5432 |                                                 |
| Keycloak 26   | 容器         | 8180 | 开发 realm 与一个测试用户，首次启动时导入        |
| mock 模型服务 | 主机进程     | 8082 | 仓内实现，OpenAI 兼容，支持流式与非流式          |
| manage-api    | 主机进程     | 8080 | 只在本机监听；浏览器经 5173 的代理访问它         |
| model-gateway | 主机进程     | 8081 | 桌面与 CLI 直接访问，不经代理                    |
| console       | 主机进程     | 5173 | 唯一的来源；把 `/em/*`、`/connect/*`、`/interaction/*`、`/auth/callback/*` 与发现文档代理到 8080 |

- `pnpm dev` 一次起四个主机进程。它先用 `scripts/dev-env.mjs` 生成 `deploy/dev/apps.env`（随机密钥，权限 600，已被 git 忽略），再用 Node 自带的 `--env-file` 把它读进环境，各应用原样继承。应用自身不读 `.env` 文件。
- 颁发者就是 `http://localhost:5173`，`ZM_PUBLIC_BASE_URL` 与 `ZM_ISSUER` 取同一个值。端口不能换：它写死在 `apps/console/vite.config.ts` 里，是颁发者地址的一部分。
- 环境文件只在不存在时生成。改了生成脚本之后，要先删掉它再重新生成。

镜像统一带可配置的仓库前缀，默认走国内可达的镜像站。

### 控制台骨架

- 页面只有两个：未登录时的登录页，和登录后的用量明细表（最新的在前，每页 50 条，可继续加载）。另有一个“退出”，走第 4 节的流程。
- 与管理接口、OIDC 端点同源，代码里只写以 `/` 开头的相对地址。生产构建是静态文件：反向代理要把 `/callback` 也指到 `index.html`，并把与开发时相同的那组路径转给管理接口。
- 客户端标识是部署期配置，不打进构建产物。构建产物里带一个 `runtime-config.js`，由入口脚本在容器启动时按环境变量重写；缺了它，应用拒绝启动并说明缺什么。开发时这个文件由 Vite 从进程环境现生成，来源只有 `apps.env` 一处。
- **令牌只放在内存里，不写 `localStorage`。** 那里的内容，任何一段被注入的脚本都读得到。代价是刷新页面后要重新点一次登录；颁发者那边还有会话，所以不会再出现登录表单。访问令牌到期前自动用刷新令牌续期。
- 登录回调在渲染之前处理，整页只处理一次：回调地址里的授权码用过即废。失败时如实显示原因，并把地址栏里的授权码换掉。
- 发请求时现取当前的令牌，不把令牌当作属性在组件之间传递：访问令牌会被续期，传属性会让整张表随之重新加载。
- 用量数据在显示前用 `@zm/contracts` 里的同一份 zod 定义校验；与契约不符就报错，不当作“没有数据”。

## 10. 验收

1. `pnpm test` 与既有门禁全绿。
2. 集成测试针对运行中的开发栈：
   - 服务账号换到令牌，令牌能由公钥验签，声明符合第 4 节。
   - 授权码加 PKCE 的完整流程走通，经过 Keycloak 登录页，最终换到带 `sub` 的令牌。
   - 换到的访问令牌能在本地验签（是 JWT），范围与申请的一字不差，并下发刷新令牌。
   - 用刷新令牌续期成功：换到的令牌仍属于同一个用户，范围不变，并继续下发刷新令牌。
   - 撤销刷新令牌后，它不能再用来续期。
   - 非流式与带 usage 的流式请求各产生一条用量，token 数精确；缺 usage 的流式请求记为 `missing`。
   - 无效令牌返回 401 且不产生用量；未知模型返回 404。
   - 用量明细接口按时间倒序返回。
   - 对外地址只认配置：伪造 Host、转发头，都改变不了发现文档里的端点；请求行写成完整地址的被拒绝。
   - 身份令牌带显示名；带受众的访问令牌调用户信息端点得到 401。
   - 退出登录：确认之后回到登记过的地址；之后同一浏览器再发起授权，得到 `login_required`。
   - 集成测试用的 Cookie 罐按路径挑着发，与浏览器的规则一致。
3. 出口：`scripts/step1-exit.sh` 用 curl 完成服务账号换令牌、调网关，然后从数据库里读出那一条用量。**脚本对数据库只读**：它连接时把数据库会话设成只读，写操作会被数据库拒绝。服务没在运行时脚本必须以非零状态退出。
4. 控制台在真实浏览器里走通：登录、显示名、用量表、退出。这一条只能人工验证，实际执行情况记在开发启动计划的执行记录里。

## 11. 已知取舍

- 交互式登录的集成测试脚本化地填写 Keycloak 登录表单。Keycloak 升级可能改页面结构，届时测试要跟着改。这是把浏览器流程自动化的代价。
- 公共客户端的回调地址必须精确登记。企业版客户端用固定端口的回环地址或自定义 scheme，不能用随机端口。
- 开发态的 OIDC 签名密钥每次启动重新生成。重启后旧令牌全部失效，这对开发是可接受的；正式部署由配置提供密钥。
- **吊销不会让已签发的访问令牌立刻失效。** 访问令牌由管理接口和网关在本地验签，颁发者撤销令牌后无法通知它们。所以吊销的保证是“不能再续期”，已签发的访问令牌直到自然过期前（最长 15 分钟）仍然有效。让设备吊销立即生效属于纵向链路 6，届时要么回查颁发者，要么各服务共享一份吊销名单。
- **退出登录不会结束客户身份系统那边的会话。已决定暂不处理。** 管控平面结束的是自己的会话。之后同一浏览器再点登录，会被客户身份系统直接认作已登录，**不会再要求口令**，在共用的电脑上挡不住下一个人以同一个账号进入控制台。2026-11-23 用户决定暂不考虑共用电脑的场景，所以不补。如果以后要补：给鉴权适配器增加“请客户身份系统结束会话”的能力，并在客户那边登记一个新的回跳地址。
- 控制台的令牌只在内存里，刷新页面后要重新点一次登录（见第 9 节）。
- 访问令牌的 `scope` 里除了业务范围，还带着 `openid`、`profile` 这些 OIDC 范围。它们对管理接口与网关没有意义，接口只核对各自需要的业务范围，所以不影响功能；范围列表可以收窄到只剩业务范围，本期没有动。
